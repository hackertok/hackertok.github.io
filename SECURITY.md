# Security Policy

## Supported Versions

| Version | Supported          |
|---------|--------------------|
| Latest  | :white_check_mark: |

Only the latest released deployment of HackerTok receives security updates. Older releases are not maintained.

## Reporting a Vulnerability

**Please do not report security vulnerabilities through public GitHub issues.**

Instead, please report them using [GitHub Security Advisories](https://github.com/hackertok/hackertok.github.io/security/advisories/new).

You should receive an initial response within 72 hours. If the issue is confirmed, a fix will be released as soon as possible depending on complexity.

### What to Include

- Description of the vulnerability
- Steps to reproduce
- Potential impact
- Suggested fix (if any)

## Security Measures

This project employs the following security practices:

- All GitHub Actions are pinned to full-length commit SHAs
- Automated dependency updates via Dependabot (daily)
- Dependency review on all pull requests
- CodeQL static analysis on pushes and pull requests to `main`, plus weekly scheduled scans
- OpenSSF Scorecard monitoring
- HTML sanitization via DOMPurify
- A strict Content-Security-Policy delivered via `<meta http-equiv>`; inline scripts are allowed by SHA-256 hash rather than `'unsafe-inline'`, and external script/frame/connect access is limited to the Hacker News APIs, validated Web Push API origin, and Cloudflare Turnstile
- A separately deployed Cloudflare Worker with response security headers, exact-origin CORS, no credentialed CORS, 8 KB request limits, token/IP rate limiting, server-validated Turnstile admission, and a maintained HTTPS browser-relay allowlist
- Anonymous per-installation bearer tokens are stored only as hashes in D1; relay endpoints and subscription keys are encrypted at rest by D1 and scrubbed on opt-out or terminal relay expiry
- The VAPID private JWK is a Cloudflare Secret and must never be placed in GitHub variables, source files, logs, artifacts, or frontend builds
- The Turnstile secret key is also a Cloudflare Secret. Only its public, hostname-restricted site key is returned to the frontend.
- Deployed configuration omits the local-only test override, so Workers reject Cloudflare's published always-pass Turnstile credentials.
- Push Queue messages contain only D1 IDs; D1 uniqueness and fenced leases provide the authorization and idempotency boundaries rather than trusting Queue payload data

### Accepted GitHub Pages constraints

GitHub Pages serves static files and cannot set HTTP response headers, which limits a few defenses to what a `<meta>` CSP can express:

- No clickjacking protection. `frame-ancestors` is ignored when a CSP is delivered via `<meta>`, and `X-Frame-Options` cannot be sent, so the site can be embedded in a frame.
- No CSP violation reporting. `report-to`/`report-uri` require a response header and a collection endpoint, neither of which is available; the build instead fails if any executable inline script in the built HTML lacks a CSP hash, and the e2e suite asserts the deployed policy is violation-free.

These constraints apply to the static Pages frontend. The Cloudflare Push
Worker does set HTTP security headers on its own responses.

## Web Push operational security

- CORS is browser policy, not API authentication. Subscription writes and
  deletion require the random 32-byte bearer token generated by that browser;
  the first write for an unknown token additionally requires a fresh,
  server-validated Turnstile token.
- The self-test endpoint sends fixed content only and is heavily rate-limited;
  it is not an arbitrary notification-sending API and cannot open the global
  delivery circuit.
- Logs must never include full endpoints, subscription bodies, encryption keys,
  bearer tokens, or `Authorization` headers.
- A subscription is relay-verified only after an accepted delivery. Endpoint or
  key reconciliation clears that evidence.
- Legacy installations without retained acceptance evidence are quarantined as
  unknown until a `2xx`: they are not deleted by one suspect fault and cannot
  contribute to the global circuit.
- Treat sender/auth relay faults from unverified subscriptions as local. A
  single verified subscription also remains local; open the delivery circuit
  only after the same fault class correlates across three distinct verified
  subscriptions within five minutes.
- Unknown opt-out tombstones use a maintained retained-row counter rather than
  a per-request table scan, are bounded, and repeated deletion of an already
  disabled token is write-free.
- Restore the offline VAPID recovery copy if a secret is lost. If compromise is
  possible, follow the rotation and client-repair runbook in
  [worker/README.md](worker/README.md).
- Stored alert data, relay involvement, and deletion/retention behavior are
  described in [PRIVACY.md](PRIVACY.md).
